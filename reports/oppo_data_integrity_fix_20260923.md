# OPPO 数据正确性事故复盘与修复（2026-09-23 下午）

> 触发点：用户查看「OPPO A6x · 马来西亚」的抓取明细时，发现每一项都写着
> **「人工费 ¥50,000（物料 ¥339）」** —— 与物料费相比数量级明显失真。
>
> 排查后确认这不是"抓取失败"，而是**数据被静默写错**：三个互相独立、
> 都不会报错的缺陷叠加。本文记录根因、证据、修复与验证。

## 摘要

| # | 缺陷 | 实际影响 | 严重度 |
|---|---|---|---|
| 1 | 把**面向网页文本**的 `parse_amount` 用来解析**接口 JSON**，`"50.000"` 被读成 50000 | OPPO 全区域人工费 **×1000**，共 **3,398 行**（cn 2,182 / my 1,053 / tr 57 / mx 62 / ae 44） | **P0** |
| 2 | `getProductInfo` 与 `getProduct` 的机型集合**互不包含**，却只用了前者 | cn **204 台**（一加/realme/真我/智能电视）整季不刷新；mx 9 台含主力机 Reno13 | **P0** |
| 3 | 节点对冲只验证「**能列机型**」、不验证「**能取价**」 | de 命中 sow-cms（能列 197 台）却取价 **0 台**，整轮静默无数据 | **P0** |
| 4 | 展示层把**原币**的物料/人工费标成 `¥` | `人工费¥50,000（物料¥339）` 实为 MYR，用户会读成人民币 | P1 |

三者共同特征：**没有任何报错**。缺陷 1 产出"看起来合理"的量级、缺陷 2/3 产出"看起来跑完了"的日志。

## 1. 人工费 ×1000：解析器用错了语境

### 现象

明细弹窗里 OPPO A6x（my）每一行都是：

```
物料/人工
🔧人工费¥50,000（物料¥339）
```

物料费 339（MYR）合理，人工费 50,000 显然不可能 —— 换一块屏的人工费不可能比整机还贵几十倍。

### 根因

OPPO REBORN 接口 `getPartPriceNew` 返回的是**结构化 JSON**，其中：

```json
{
  "partName": "Screen Component",
  "retailPrice": "89.00",
  "retailPriceCurrency": "MYR",
  "laborCostAmount": "50.000",     ← 固定 3 位小数
  "laborCostCurrency": "MYR"
}
```

`vendor/executor.py::flatten_reborn_parts` 把它交给了 `normalize.parse_amount()`。

而这个函数的职责是解析**网页可见文本**——为了正确处理「德语 `1.234,56`（点=千分位）
vs 美式 `1,234.56`（逗号=千分位）」的歧义，它带了一条启发式：

> 只有一种分隔符、且只出现一次时：**小数位恰好 3 位 → 视为千分位**（`8.200` → 8200）

于是 `"50.000"` 被当作"50 千" → **50000**。

**为什么物料费没受影响**：`retailPrice` 是 2 位小数（`"89.00"`），不触发"尾 3 位"规则。
只有人工费固定用 3 位小数 —— 这个不对称正是它长期没被发现的原因。

实测各区域接口原始值（小数位整齐划一）：

| 区域 | retailPrice | laborCostAmount | 币种 |
|---|---|---|---|
| my | `89.00` / `419.00` | `50.000` | MYR |
| cn | `4499.00` / `3599.00` | `50.000` | CNY |
| ae | `600.00` / `2700.00` | `40.000` / `80.000` | AED |
| mx | `1478.30` / `615.96` | `650.000` / `240.000` | MXN |
| tr | `15180.00` / `37950.00` | `1350.000` | TRY |
| de / jp | —— | `0.000` | —— |

### 影响量化（修复前，与备份库对账）

| 区域 | 币种 | 错误值 | 正确值 | 行数 |
|---|---|---|---|---|
| cn | CNY | 50,000 | 50 | 2,182 |
| my | MYR | 50,000 | 50 | 1,053 |
| tr | TRY | 1,350,000 | 1,350 | 57 |
| mx | MXN | 650,000 / 240,000 | 650 / 240 | 62 |
| ae | AED | 40,000 / 80,000 | 40 / 80 | 44 |
| | | | **合计** | **3,398** |

另有 2,479 行为 `labor_fee=0`（ae 241 / cn 1,911 / de 155 / jp 172）——
0 无论怎么解析都是 0，故不受影响（de/jp 的接口值本就是 `"0.000"`）。

cn 另有 09-17 批次的一批正确值（200/300/580 等，来自更早的抓取路径），与污染值并存 ——
这也是它没被一眼看穿的原因。

### 修复思路：分清语境，而不是"修好"某个函数

关键判断：**`parse_amount("50.000") == 50000` 在文本语境下是对的**（德语里 `.` 就是千分位）。
问题不在函数，而在**用错了地方**。所以：

- `vendor/normalize.py` 新增 `parse_json_amount()` —— 面向接口 JSON：
  JSON 数值语法规定小数点只能是 `.`、逗号只能是千分位，故**不做任何推断**（`,` 一律删、`.` 一律作小数点）。
- `flatten_reborn_parts` 改用它。
- 同类"结构化字段被交给文本解析器"的调用一并迁移：`api_json` 遗留分支（executor + run.py）、
  `samsung_api` 的 `PART_PRICE`、`tools/refetch_failing.py`。
- **刻意保留** `parse_amount` 原行为，并在 docstring 里写清分工与本次事故 ——
  防止后来者"顺手把它修好"（那会立刻毁掉德语区文本解析：`8.200` 会从 8200 变成 8.2）。

判别口径（已写入代码注释）：

| 来源 | 该用哪个 | 例 |
|---|---|---|
| 网页可见文本（含货币符号、本地化格式） | `parse_amount` | `€488,99` / `₺14.300` / `AED 1,845` |
| 接口 JSON 字段 | `parse_json_amount` | `"50.000"` / `"4499.00"` / `"1,234.56"` |

### 回归测试

`tools/test_amount_parse.py`（不联网，纯函数）：

- A 组：`parse_json_amount` 必须把 `"50.000"` 读成 **50**（本次事故）
- B 组：不得误伤常规 JSON 价（`4499.00` / `1,234.56` / `2380.0`）
- C 组：`parse_amount` 的德语/美式/千分位行为**必须原样保留**
- D 组：**固化** `parse_amount("50.000") == 50000`（写明这是预期行为，正因如此 JSON 才必须走另一个函数）
- E 组：`None`/空串/非数字/原生数值类型的边界

`tools/verify_oppo_matrix.py` 新增 `db_labor_fee_anomalies()`：按币种设量级上限
（CNY 2000 / MYR 1000 / AED 1000 / MXN 8000 / TRY 20000），防止"×1000"类污染再次入库。

## 2. 端点集合互不包含：cn 丢了一整个子品牌群

### 发现过程

修复解析器后强制重抓，cn 仍有 **1,621 行** labor=50,000 没被刷新。
追下去发现它们全部是一加 / realme / 真我机型，抓取时间停留在 **09-20** —— 本轮重抓根本没碰过它们。

`--force` 会忽略断点续跑，所以问题不在"跳过"，而在**机型列表本身**。

### 证据：两个端点各有一半世界

实测 `getProduct` 与 `getProductInfo` 的机型集合：

| 区域 | getProduct | getProductInfo | 交集 | 仅 Info 有 | **仅 Product 有** |
|---|---|---|---|---|---|
| cn | 465 | 620 | 261 | 359 | **204** |
| ae | 99 | 196 | 86 | 110 | **13** |
| mx | 53 | 136 | 44 | 92 | **9** |
| my | 124 | 254 | 122 | 132 | **2** |
| de | 10 | 192 | 9 | 183 | **1** |
| jp | 26 | 47 | 25 | 22 | **1** |
| tr | 29 | 175 | 29 | 146 | **0** |

"仅 Product 有"的机型包括：

- cn：**OPPO 智能电视 K9 全系**、**一加 / OnePlus / realme / 真我 全系**（OPPO 集团子品牌，
  其在华售后已并入 OPPO —— 这些确实是 OPPO 中国官网备件价页上的真实在售条目）；
- mx：**Reno13 5G / Reno13 F 5G / OPPO Pad Neo / A5 Pro** 等主力机型；
- my：Enco X / Enco X3s 等音频产品。

2026-09-23 上午的"覆盖修正"把 `product_list` 从 `getProduct` 换成 `getProductInfo`
（为把 de 从 10 台提升到 192 台），代价就是**这批机型整季不再被发现、旧快照也永不刷新**。
换句话说：上午修好了 de，同时悄悄弄丢了 cn 的 204 台。

### 修复

KB 为 7 个区域新增 `product_lists`，主端点仍是 `getProductInfo`，附带端点补 `getProduct`；
`run.py` 逐端点请求、按 `marketingModelCode` 去重取**并集**。

附带端点同样走节点对冲（见第 3 节）—— 实测同一端点在 sow-cms 上返回 0 台、在 par-sow-cms 上正常，
直接复用主端点的命中节点会静默漏数据。

效果：

| 区域 | 目录机型（修复前 → 后） | 有价机型 |
|---|---|---|
| cn | 620 → **824**（补入 204） | 373 → **574** |
| ae | 196 → 209（+13） | 120 |
| mx | 136 → 144（+9） | 64 |
| my | 254 → 256（+2） | 171 |
| de | 192 → 192（+1） | 25 |
| jp | 47 → 48（+1） | 26 |

**如实说明**：非CN 区域补入的 26 台，取价后官方均无备件价（有码无价），
故**库内有价机型数未变**（非CN 合计仍 466 台）。它们的价值在于**已纳入发现范围** ——
一旦官方定价即自动入库，不必再等到有人发现缺失。cn 的 204 台则产生了实质变化：
其中 187 台一加/realme/真我机型被真正刷新，人工费从 50,000 修正为 50。

## 3. 节点误选：静默 0 价

### 现象

重抓 de 时日志一切正常，但结果是空的：

```
[reborn] sow-cms.oppo.com 发现 196 个机型（area=de）
[reborn] 取价完成 0/196 台有价，并发=6，耗时 9.4s
[done] oppo/de 本季新增 0 机型 / 0 条价
```

### 根因

`_probe_hosts_for_models` 的对冲判据是「**谁先返回机型列表**」，hedge = 3s。实测：

| 节点 | 响应 | 返回机型 | 对 de 的取价 |
|---|---|---|---|
| `par-sow-cms`（欧洲专属，KB 里排第一） | **4.12s** | 191 台 | **正常 → 25 台有价** |
| `sow-cms`（全球节点） | 0.22s | 197 台 | **全部返回空** |
| `sgp-sow-cms` | 5.87s | 197 台 | —— |

par 冷启 4.12s 超过了 3s 的宽限期，被判"慢"；0.22s 的 sow 抢先胜出。
而 sow **只服务机型目录、不服务 de 的取价** —— 逐台验证：同一批 marketingModelCode，
par 上 `OPPO Find X9` 能取到 12 行价，sow 上四台全部 0 行。

这是最难察觉的一类失效：**没有异常、机型列表也拿到了、只是整轮 0 价**。
若不做"取价结果"层面的核对，会误以为"OPPO 德国官网没有备件价"。

### 修复

KB 的候选顺序本就把「区域专属正主」排在第一位，所以给**第 0 个候选**单独的宽限期：
新增常量 `_PROBE_FIRST_HEDGE_S = 8.0`（可用 KB `probe_first_hedge` 覆盖），
其余候选仍用 `hedge = 3s`。正主本来就不该和兜底节点用同一个宽限期。

修复后：

```
[reborn] par-sow-cms.oppo.com 发现 191 个机型（area=de）
[reborn] 取价完成 25/191 台有价，并发=6，耗时 60.3s
[done] oppo/de 本季新增 25 机型 / 155 条价
```

## 4. 展示层：原币金额被标成 ¥

明细弹窗与矩阵提示把**原币**的物料/人工费统一加了 `¥` 前缀：

```js
labor = `🔧人工费¥${fmt(pc.labor_fee)}（物料¥${fmt(pc.material_fee)}）`;
```

`labor_fee` 存的是**当地货币**（MYR/AED/TRY/MXN/CNY），标 `¥` 会让用户把
「人工费 339 林吉特」读成「339 元人民币」——与旁边的「CNY 折算」列直接冲突。

已改为显式带币种，共 4 处（矩阵徽标、单元格 tooltip、明细弹窗、备件清单）：

| 位置 | 修复前 | 修复后 |
|---|---|---|
| 矩阵单元格徽标 | `🔧人工费¥50` | `🔧人工费 50 MYR` |
| 单元格 tooltip | `物料¥339 人工¥50` | `物料 339 / 人工 50 MYR` |
| 明细弹窗 | `人工费¥50,000（物料¥339）` | `人工费 50（物料 339）MYR` |
| 备件清单 | `🔧 ¥50` | `🔧 50 MYR` |

并在图例里写明「人工费按**当地货币**计价」。
